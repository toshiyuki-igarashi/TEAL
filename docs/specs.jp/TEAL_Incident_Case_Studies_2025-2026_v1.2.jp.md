# 侵害後実行制御：近年のサイバーインシデントに関するケーススタディ

## TEAL（Trusted Execution & Authorization Layer）への示唆

**技術ケーススタディレポート | バージョン 1.2 | 2026年11月8日**  
**調査対象期間:** 2025年11月7日 – 2026年11月7日  
**スコープ:** インシデントの証拠、現実的な攻撃経路、TEAL の適用可能性、および実践的な検証シナリオ

> **重要な解釈ルール：** 本レポートは、**「報告された事実（Confirmed/reported facts）」**、**「技術的推論（Technical inferences）」**、および**「仮説的 TEAL 防御策（Hypothetical TEAL defenses）」**を明確に区別しています。被害組織に TEAL が導入されていたと主張するものではなく、また提案された制御策が実際の攻撃を確実に阻止できたと断定するものでもありません。Windows 製品やアプライアンスが関与するインシデントについて、防御の議論では同等の管理機能を備えた**「Linux ベースの実装」**を明示的に仮定（反実仮想）しています。事実としてのインシデント記述において、実際の製品アーキテクチャが Linux に暗黙のうちに置き換えられることはありません。

## エグゼクティブ・サマリー

近年のサイバー攻撃は、実質的に異なる 3 つの侵害後活動（Post-Compromise Activity）の形態を浮き彫りにしています：

1. **信頼されていない OS 実行：** 攻撃者は足がかりを得た後、追加コマンドの実行、ファイルの改ざん、または悪意のあるコードの実行を行います。TEAL のファイル／実行ポリシーエンジンおよび基本的な多者承認（MPA: Multi-Party Authorization）は、これら実行ポイントに介入できる可能性があります。
2. **正当な管理権限の悪用：** 攻撃者は管理プレーン（Management Plane）に到達し、仮想マシンの削除、エンドポイントの初期化（ワイプ）、ソフトウェア配布などの正規の機能を呼び出します。TEAL は、危険な操作が独立した、呼び出し頻度の低い Linux 実行可能ファイルによって行われる場合に有効に機能します。一方、常駐する管理デーモンやリモート API に対しては、通常、操作境界（Operation Boundary）における追加の制御が必要となります。
3. **業務トランザクションの不正利用：** 攻撃者は、銀行送金など、OS の観点からは技術的に正当な指示を発行します。最終的なゲートは、汎用的なファイル／実行ポリシーではなく、アプリケーション独自の業務承認レイヤーでなければなりません。

**主要な発見（Principal Finding）：** 最適な適用ポイントは、**管理ソフトウェアがどのように運用されているか**に依存します。頻度の低い破壊的ユーティリティは、TEAL による `EXEC` 制御および MPA の強力な適用候補です。定期メンテナンス用ユーティリティは、さらにアイデンティティ、時間窓（Time Window）、信頼できる起動コンテキストによって制限できます。常駐する管理サービスに対しては、起動時の認可だけでは不十分であり、実際の破壊的操作自体を個別に認可する必要があります。この区別は、特に Beget および Stryker のインシデントにおいて重要です。

**計画中のログイン出自（Login-Provenance）ベースライン：** 次期 TEAL リビジョンでは、ユーザーの環境変数を信用せず、カーネル保護された認証連動セッション出自を実装することを前提とします。これは確約された設計要件であり、Alpha で動作実証済みの機能ではありません（第 6.4 節〜第 6.5 節）。

**カーネル境界の拡張：** 第 8 章では、Alpha におけるカーネル信頼の前提と、提案されているセキュアブート／メジャードブート（Verified/Measured Boot）、TPM ベースのリモート証跡、独立したウォッチドッグ監視、外部からの強制隔離、および信頼できる復旧手順を区別して論じます。これらは計画中の補完的対策であり、任意のカーネル侵害に対する実証済みの防御策ではありません。

**証拠の確信度：** Ivanti のエクスプロイトや Trivy / LiteLLM のサプライチェーン攻撃については、コマンドレベルの詳細な観測記録が存在します。Beget、Arkéa、Stryker については、「何が行われたか」に関する比較的強力な証拠が存在するものの、「初期の信頼境界がどのように突破されたか」についての公開証拠は不完全です。

## 1. 調査手法と技術的境界

### 1.1 証拠の分類ラベル

- **確認済み／報告済み（Confirmed/reported）：** 被害組織の公式発表、規制当局の勧告、ベンダーのインシデント分析、または直接の取材に基づく調査報道に記載された事実。出典とその限界を明記します。
- **推論（Inferred）：** 観測された結果を説明し得る、技術的に現実的な攻撃メカニズム。攻撃者の特定や、確定したエクスプロイト経路を意味するものではありません。
- **仮説的制御（Hypothetical control）：** 影響を受けたワークフローの Linux 実装を想定したセキュリティ設計であり、被害組織の実際の設定を主張するものではありません。

情報源は 2026年11月7日 時点で一般に公開されている資料に基づいて確認されています。インシデントの内容および復旧の見積もりは、当該組織によって更新される可能性があります。

### 1.2 TEAL の現行機能と拡張計画

プロジェクト文書では、カーネル側でのインターセプト、`teald` ポリシー評価、認可決定、短寿命チケット、および監査ログを組み合わせた Linux LSM ベースのアーキテクチャが規定されています。TEAL のショートペーパーでは、**Alpha 実装**のスコープを、コアとなるファイル／実行インターセプト、基本的な MPA／承認フロー、Fast Path キャッシング、および監査機能の検証と定義しています。また、**TEAL-NET、TPM／メジャードブート、暗号学的認可の強化**を将来の課題として位置づけています。[T1–T3]

したがって、本レポートでは以下の基準を用います：

| 制御機能 | 本分析におけるステータス | 重要な制限事項 |
|---|---|---|
| ファイル／実行のインターセプトおよびポリシー検証 | Alpha コア機能 | 検証対象のカーネル／ビルドにおいて、`WRITE`、`UNLINK`、`RENAME`、および特殊デバイスの網羅性を検証する必要がある。 |
| 基本的な MPA および短寿命認可チケット | Alpha コア機能 | 承認者の堅牢な隔離、チケットスコープ、および侵害されたプロセスの再利用に対する耐性の検証が引き続き必要である。 |
| 信頼できるログイン出自および時間窓ポリシー | 設計／開発方針 | 信頼性の高い認証済みセッション出自と、強制力を持つ時間マッチャーが前提条件となる。 |
| TEAL-NET 送信制限 | 計画中／拡張機能 | `connect()` ゲート単体では、確立されたソケット経由で送信されるすべてのデータを意味論的に認可することはできない。 |
| 管理 API またはトランザクションレベルの認可 | 外部連携または新規機能 | API／トランザクション実行主体側での明示的な連携・組み込みが必要である。 |
| カーネル侵害に対する耐改ざん性トラストルート | 現行 Alpha 保証範囲外 | カーネルエクスプロイトやコントロールプレーンの侵害により、ローカルの LSM がバイパスされる可能性がある。 |

許可された**プロセスアイデンティティ**は、そのプロセスが実行するすべてのアクションが許可されていることの証明にはなりません。逆に、root 特権であっても保護されたリソースへのアクセスが無条件に正当化されるわけではありません。これこそが TEAL の中心的な設計思想です。[T1, T2]

## 2. ケーススタディ A — Beget：管理プレーンへのアクセスと破壊活動

**組織:** Beget（ロシアのホスティングおよびクラウドプロバイダー）  
**インシデント発生日:** 2026年11月2日  
**主要ソース:** Beget 公式インシデント通知および公式アップデート [R1, R2]

### 2.1 公に報告されている事実

Beget は、11月1日から2日にかけてインフラに対する攻撃を受けたと公表しました。公開されたタイムラインによると、攻撃者はモスクワ時間 **02:00 頃**に管理サーバーへのアクセスを取得し、**02:30** にサーバーデータの消去を目的としたソフトウェアを起動。**02:40** に不正アクセスが検知され、封じ込め措置として **02:55** までに対象サーバーがネットワークから切断されました。Beget の公式チャンネルでは、管理コントロールプレーンへのアクセスと、データをゼロクリア（ゼロ埋め）するスクリプトの実行についても言及されています。影響を受けたサービスの復旧は段階的に進められました。[R1, R2]

この一連の経緯は、運用上の重要な障害モードを示しています。すなわち、**侵害された管理プレーンは、個々の顧客 VM に対して個別に攻撃を成功させる必要なく、その配下にある膨大な顧客ワークロードに被害を及ぼすことができる**という点です。

### 2.2 確定していない事項

公知の情報では、初期脆弱性、認証情報の窃取の有無、正確な権限昇格メカニズム、管理システムの実装言語、データ破壊に直接のファイルシステムコール／Raw ブロックデバイスアクセス／クラウド管理 API のいずれが使われたのかは特定されていません。これらは確定した事実ではなく、複数の可能性として扱う必要があります。

### 2.3 技術的に現実的な分岐（仮説）

| 仮説 | 破壊的実行ポイント | TEAL への示唆 |
|---|---|---|
| A. 攻撃者が独立したワイプ実行ファイルまたはスクリプトを起動した | `execve` およびその後の保護対象ファイル／デバイス操作 | 頻度の低い破壊的バイナリに対するポリシーにより、起動前に MPA を強制できる。 |
| B. 攻撃者が Linux プロセスからマウントされたストレージを変更・削除した | 保護されたファイルの open、write、unlink、rename、またはブロックデバイスアクセス | フックの正確な網羅性を前提として、オブジェクト／操作レベルの制御で阻止できる可能性がある。 |
| C. 攻撃者が特権ストレージ／VM 管理 API を呼び出した | 管理 RPC/API および下流サービスの動作 | 呼び出し元に対する Linux LSM 単体では、「VM の削除」というセマンティックなトランザクションを認識できない可能性がある。 |

### 2.4 反実仮想 Linux 管理プレーン設計

定常的な管理業務と破壊的操作が分離されている環境を想定します：

```text
非特権監視サービス（常時稼働）
 |
 +--> 読み取り専用のステータスおよびインベントリ取得（通常の allow）
 |
 +--> 破壊的メンテナンスのリクエスト
 |
 v
 /usr/local/sbin/vm-destroy（稀に実行される EXEC）
 |
 TEAL ポリシー検証
 |
 独立した MPA 承認
 |
 スコープを絞った短寿命認可チケットの発行
 |
 認可された削除処理の実行
```

この設計のもとでは、管理シェルを奪取した攻撃者であっても、承認なしに `vm-destroy` を実行することはできません。**ただし**、これが成立するのは、代替となる削除経路（直接のストレージアクセス、シェルユーティリティ、特権デーモン、管理 API、バックアップの削除など）が遮断されているか、同等にゲートされている場合に限られます。特権管理プロセスに対して包括的な例外（ブランケット・アロウ）を 1 つでも設けると、保護は無効化されます。

大量削除を抑止するためのより強固な設計では、承認を特定の対象セット、操作タイプ、メンテナンス時間窓、有効期限に厳密にバインドし、単なるプロセスの起動時だけでなく**破壊的操作そのもの**をチェックします。提案されているスライディングウィンドウ閾値は、承認済みの破壊的アクションの回数をカウントし、**コミットされる前に**新たなアクションを拒否またはエスカレーションします。事後アラートでは、すでに削除されたデータを保護することはできません。

### 2.5 防御の評価

- **高い適合性：** 呼び出し頻度の低いスタンドアロンのワイプ／削除ツール、および保護されたローカルファイルシステム操作。
- **条件付きの適合性：** 各削除処理に対してスコープの限定されたワーカープロセスを起動するストレージデーモン。
- **連携なしでは不十分：** 正当なボリューム削除 API リクエストを発行し続ける常駐型クラウドコントローラー。
- **追加の安全策：** 独立した管理信頼ドメインに配置された、改ざん不能なイミュータブル・バックアップ。TEAL はデータ復元力の代替にはなりません。

## 3. ケーススタディ B — Crédit Mutuel Arkéa：サードパーティプラットフォーム経由の不正送金

**組織:** Crédit Mutuel Arkéa（フランス）  
**公表日:** 2026年11月4日  
**主要ソース:** 銀行の初期発表および追加情報 [R3, R4]、Reuters 報道 [R5]

### 3.1 公に報告されている事実

同行は、サイバー攻撃により不正な取引が行われたと発表しました。追加の発表によると、攻撃者は**Crédit Mutuel Arkéa が保有する口座**を利用して他の金融機関へ資金を移動させ、その後暗号資産への換金が行われた可能性があります。攻撃者の侵入経路は同行傘下の Fortuneo ではなく、**サービスプロバイダーのプラットフォームを経由して** Arkéa に到達したと明記されています。顧客資産への影響は報告されていませんが、一部の送金に遅延が生じました。ロイターはその後、約 **1億ユーロ** が詐取され、最終的な回収額・損失額の算定が続けられていると報じました。[R3–R5]

### 3.2 不明な初期侵害要因

当該プロバイダーの社名は公表されていません。以下の疑問は未解決のままです：プロバイダーのホストが侵害されたのか？ API キーやサービスアカウントが窃取されたのか？ サードパーティアプリケーションの認可ロジックがバイパスされたのか？ 事前に承認されていた送金ワークフローが悪用されたのか？ 2つの独立した認可ドメインが関与していたのか？ **公開されている証拠の中に、これらを決定づけるものはありません。**

したがって、「サプライヤー側で TEAL が無力であった」と結論づけるのは誤りです。保護された Linux ホスト上で実行されていた場合、認証情報ファイルへのアクセス、悪意のある実行（exec）、あるいは未認可の外部接続を阻止できた可能性があります。同様に、通常の TEAL ファイル／実行制御のみで最終的な不正送金を確実に阻止できたと主張することも誤りです。

### 3.3 攻撃チェーンを遮断するための 2 つの独立した境界

**第一の境界：プロバイダー環境。** Linux の反実仮想において、プロバイダーの署名用認証情報、サービスアカウント情報、デプロイメントパス、および通常と異なる実行可能ファイルを保護し、銀行のエンドポイントへのアクセスを認可されたソフトウェアのみに制限します。ただし、メモリ上にすでに展開されている API トークンの窃取、侵害された信頼済みサービス、またはアプリケーション内部の欠陥は、OS レベルのチェックをすり抜ける可能性があります。

**第二の境界：銀行のトランザクション実行基盤。** 送金元口座、受取人、金額、通貨、送金 ID、承認された目的、時間窓、および累計限度額を含む**送金指示そのものに対して業務認可を適用**します。決済ネットワークへの「接続許可」は、無制限に「資金を移動させる許可」を意味してはなりません。

### 3.4 通常の業務統制で十分であった可能性（バイパス不能であれば）

従来の多層承認ポリシーが適用されます：

- 定常的で低リスクな支払いは、委任された運用限度額の範囲内で処理を許可。
- 高額または異常な支払いは、引き上げられた財務認可を要求。
- 例外的な送金は、職務分掌のもと、複数の認可された役員または取締役による独立した承認を要求。
- 個別の承認閾値を下回る連続送金は、**累計限度額**および受取人／リスクチェックによって制限。

この閾値が機能するのは、**送金を執行するシステム**が承認を独立して検証し、承認者が申請者と別人であることを保証し、承認を**正確な**支払い指示と暗号学的またはトランザクション的にバインドしている場合に限られます。過去に承認された認証情報を、内容の異なる送金に再利用することはできなくなっていなければなりません。また、常時稼働するリアルタイム決済には、高度に設計された自動化ポリシーレーンが必要であり、すべての通常送金に役員の承認を要求することは運用上現実的ではありません。

**反実仮想の結論：** 独立して執行され、バイパス不可能な業務認可が存在していれば、仮にプロバイダーが侵害されていたとしても、未認可の高リスク送金は阻止できた可能性があります。公開情報からは、Arkéa にそうした統制が欠落していたのか、例外が存在したのか、あるいは既存の統制が攻撃者によってバイパスされたのかは不明です。

### 3.5 TEAL のスコープへの示唆

このインシデントは、単に「TEAL の対象外」というわけではありません。プロバイダーの侵害には TEAL に関連する Linux レベルの活動が含まれていた可能性がありますが、最終的な送金認可の境界は業務トランザクション層に存在します。TEAL のような MPA サービスをトランザクション実行基盤に統合することはシステムアーキテクチャとして可能ですが、**TEAL Alpha で実証された機能ではありません**。

## 4. ケーススタディ C — Stryker：正当なエンドポイント管理機能の破壊的悪用

**組織:** Stryker Corporation（米国）  
**インシデント発生日:** 2026年3月11日  
**主要ソース:** Stryker の 3月12日および16日の声明、CISA の 3月18日付ガイダンス [R6–R8]

Stryker は、攻撃者が正規のモバイル／エンドポイント管理システムである **Microsoft Intune** を悪用して内部仮想インフラをワイプし、ノート PC、モバイル端末、仮想サーバーを動作不能にしたと発表しました。影響を受けた環境ではランサムウェアやマルウェアは検知・展開されていないと報告されています。CISA はこれを受け、エンドポイント管理システムの堅牢化と適切な管理的保護策の導入を促す勧告を公開しました。初期侵入経路および正確な特権奪取の手法は、これらの報告では明らかにされていません。[R6–R8]

評価のため、Intune を**同等の Linux ベースのエンドポイント管理サービス**に置き換えて検討します。設計上の重要な変数は、*ワイプ機能がどのように呼び出されるか*です。

### 4.1 管理ツールの運用パターン I — 稀に実行されるバイナリ

```text
メンテナンス管理者 -> /opt/manage/bin/fleet-wipe -> リモートエンドポイント
 ^
 TEAL EXEC + MPA ゲート
```

`fleet-wipe` が例外的な運用のためにのみ起動される場合、独立した承認なしには `EXEC` を拒否するポリシーは、シンプルかつ非常に効果的な防御策となります。実行バイナリは、承認されたホストリストやジョブマニフェストに厳密に制限される必要があります。攻撃者が別のデーモン、シェル、または API を介して同一のワイプを実行できる場合、このバイナリのみをゲートするのでは不十分です。

### 4.2 パターン II — スケジュールされたメンテナンス

定期的な検査やメンテナンス用バイナリは、専用の UID、認証されたジョブ出自、想定された時間窓、検証されたバイナリ同一性、および限定された許可アクションセットのもとでのみ実行を許可できます。許可されたメンテナンス時間内であっても、破壊的操作は例外として扱われるべきです。単に UID と時刻を照合するだけでは、侵害された管理者がジョブを偽装したり、許可時間まで待機したりした場合に脆弱となります。

### 4.3 パターン III — 常時稼働デーモン

```text
Webコンソール/API -> エンドポイント管理デーモン（常時稼働中）
 |
 +--> ステータス/テレメトリ取得（許可）
 +--> フリートワイプ（個別の操作ゲートが必要）
```

デーモン起動時の `EXEC` チェックでは、後から送信される認証済み API リクエストを止めることはできません。対策としては、ワイプ処理を個別に起動される特権ヘルパープロセスに切り離す（その上で `EXEC` ＋引数／ジョブの認可を強制する）か、あるいは API のワイプトランザクションに独立した MPA 決定を直接組み込むことが挙げられます。これが、**「プログラム実行の承認」**と**「管理アクションの承認」**の決定的な違いです。

## 5. 十分な技術的証拠が存在するその他のインシデント

### 5.1 Ivanti EPMM — 認証前コードインジェクション（2026年1月〜3月）

Telekom Security は、Ivanti Endpoint Manager Mobile アプライアンスに対する CVE-2026-1281 および CVE-2026-1340 の悪用を文書化しました。攻撃者が制御可能な Web 入力がサーバー側の Bash 評価に到達し、未認証のリモートコード実行が可能となっていました。レスポンダーは、コマンド実行、JSP Web シェルの設置試行、および侵入後の永続化活動を観測しました。[R9]

**Linux 反実仮想：** 侵害された Web サービスの実行主体が予期しない `EXEC`（シェル、ダウンローダー、特権ユーティリティ）を試みた場合、TEAL はそれを拒否できます。また、ファイルシステムルールにより Web シェルの書き込みを阻止できる可能性があります。ただし、サービスが正規の業務として任意のコマンドを呼び出している場合や、広範な実行チケットを継承している場合、保護性能は低下します。さらに、すでに実行中の信頼済みプロセスの内部メモリ状態を完全に書き換えるエクスプロイトは、新たな `execve` を発生させない可能性があります。

**検証可能な仮説：** HTTP エントリポイントの侵害は成功するものの、永続化が確立される前に未認可の子シェルまたは Web シェルの書き込みが阻止される。

### 5.2 Trivy — 信頼された CI/CD 配布チャネルの汚染（2026年3月）

Aqua Security は、攻撃者が GitHub Actions の自動化基盤から特権認証情報を取得し、不完全なローテーションの隙を突いてアクセスを維持した上で、3月19日に悪意のある Trivy アーティファクトを公開したと報告しました。攻撃者は `trivy-action` の **77 バージョン中 76** のタグ、および 7 つの `setup-trivy` タグをリダイレクトしました。正規のタグ名が攻撃者の制御するコードを指すようになり、下流の CI/CD ジョブが認証情報窃取に晒されました。[R10, R11]

**TEAL への示唆：** 厳格なシークレットファイルへのアクセス制御、制限されたプロセス実行、および外部宛先の制限により、ペイロードの影響を局所化できます。しかし、侵害されたスキャナーは CI 環境において信頼されたツールとして実行されます。実効性の高い対策には、フルコミット SHA によるピン留め、アーティファクトの来歴（Provenance）検証、短寿命トークン、およびリリース用認証情報の完全な隔離も含まれます。プログラムの同一性や過去に承認された CI ジョブを、無制限の信頼権限として扱ってはなりません。

### 5.3 LiteLLM — 下流 Python パッケージの侵害（2026年3月）

JFrog の調査により、LiteLLM の CI 環境が侵害された Trivy バージョンを使用していたことで CI 認証情報が漏洩し、悪意のある PyPI リリース `litellm` **1.82.7 および 1.82.8** の公開に悪用された経緯が再現されました。悪意あるパッケージには `proxy_server.py` およびインタプリタ起動時に Python コードを実行できる `.pth` ファイル内にペイロードが含まれており、クラウド／SSH／Kubernetes の認証情報を探索して外部流出と永続化を試みました。[R12]

**TEAL への示唆：** 実行バイナリ自体は正規の Python インタプリタです。インタプリタ、インポートフック、プロセス内の悪意あるロジックは、実行ファイルのパスだけで安全性を判定することはできません。ファイルシステムへのアクセス制限と送信制御（Egress Protection）は有効ですが、すでにメモリに読み込まれている環境変数のシークレットや、認可済みプロセスを介した操作は残余リスクとして残ります。信頼できないパッケージやサブプロセスへの広範なチケット継承は避ける必要があります。

### 5.4 Fortinet FortiCloud SSO — 管理認証バイパス（2026年1月）

Fortinet は、FortiCloud SSO における **CVE-2026-24858** の悪用を報告しました。この機能が有効になっている場合、適格な FortiCloud アクセス権を持つ攻撃者が他の顧客に登録された脆弱なデバイスにログイン可能となっていました。観測されたその後の活動には、デバイス設定のダウンロードや、永続化を目的としたローカル管理者アカウントの作成が含まれていました。[R13, R14]

**Linux 反実仮想：** 管理ログインが成功した後であっても、新しい特権アカウントの作成、セキュリティ構成の変更、または機密性の高いデバイス設定のエクスポートには、個別の認可を要求することができます。常駐管理プロセスで実装されたアプライアンスでは、単なる初回 `EXEC` チェックではなく、アクションを認識するチェックが求められます。

### 5.5 GMO お名前.com デスクトップクラウド — 管理サーバーを踏み台にした顧客 VM への横展開（日本、2026年）

GMO は、一部の顧客環境に不正なプログラムが配置されたことを公式に開示しました。ITmedia が報じた 11月2日の記者会見内容によると、8月5日に顧客のリモートデスクトップ VPS への初期侵入が発生し、8月17日までに管理者アカウントが奪取されて管理サーバーに侵入。9月20日から10月14日にかけて、最大 **26,739 台の潜在的に影響を受ける顧客 VM** に対してマルウェアが展開されました。正確な初期エクスプロイト経路は非公開のままです。[R15, R16]

**Linux 反実仮想：** 顧客側での実行バイナリおよびシークレットへのアクセスを制限するとともに、管理サーバーからのソフトウェア展開を専用のアップデートヘルパー経由、または署名付きパッケージと対象スコープの事前承認を介して制御することが考えられます。すでに稼働している特権配布サービスが悪用された場合は、API／トランザクションレベルでの強制力が必要となります。なお、潜在的に影響を受ける最大 VM 数を、侵害が確認された確定数と同一視してはなりません。

## 6. 管理ソフトウェアに対する TEAL の汎用制御モデル

Beget、Stryker、GMO から得られる共通の設計教訓は、**管理ソフトウェアはプログラムの名前だけでなく、その「呼び出しパターン」によって分類されるべきである**という点です。

| デプロイメントパターン | 例 | 低複雑度の制御策 | 残余課題 |
|---|---|---|---|
| 稀に実行されるスタンドアロンユーティリティ | `vm-destroy`, `fleet-wipe` | TEAL `EXEC` ＋ 独立した MPA、スコープを絞ったチケット | 代替ツール/APIの存在、承認済み実行ファイル/引数の悪用 |
| スケジュール実行ツール | 夜間メンテナンス、定期監査 | UID ＋ 認証済みスケジューラ出自 ＋ 検証済みバイナリ ＋ 時間窓 | 攻撃者が許可時間窓まで待機、またはスケジュールされたジョブの乗っ取り |
| ヘルパーを生成する常駐型サービス | コントローラー -> 特権削除ヘルパー | コントローラーを通常 allow、ヘルパーの `EXEC` およびジョブマニフェストをゲート | 直接のAPI呼び出し、特権ソケット、保護されていないヘルパーによるバイパス |
| 内部で処理を完結する常駐型サービス | デーモンが直接削除/ワイプAPIを呼び出し | サービス内部での明示的な操作/トランザクション認可 | ローカルの `EXEC` は起動時のみ発生、OSフックではトランザクションを識別不能 |
| 外部業務ワークフロー | 銀行送金指示 | 独立した業務認可および職務分掌 | OSレベルの属性には受取人、金額、目的などの情報が符号化されない |

### 6.1 `EXEC` 単体制御が有効に機能するための前提条件

`EXEC` ゲートがシンプルで強力な防御となるのは、**以下のすべてが成立する場合に限られます**：

1. 危険な機能へのアクセス経路が、ゲートされたプログラム以外に存在しないこと。
2. 被害をもたらすアクションの**前**に実行イベントが発生すること（すでにその機能を保持した状態でプロセスが稼働し続けていないこと）。
3. アイデンティティおよび出自の検証が、攻撃者が改変可能な環境変数に依存せず、カーネルまたは認証基盤に裏付けられた信頼できるコンテキストを使用していること。
4. 認可のスコープが、運用モデルが要求する正確なアクション、対象、有効期間に限定されていること。
5. 認可されたプログラムが、未検証の引数や置き換え可能なスクリプト／設定によって自由に変造（Repurposed）できないこと。
6. ローカル管理者権限を持つ攻撃者が、TEAL を無効化したり、ポリシーや承認を改ざんしたり、基盤となるより広範な制御インターフェースを直接操作できないこと。

これらが満たされない場合、**操作レベルの制御（Operation-level controls）**が必要になります。適切な実装では、害のない監視機能と、めったに実行されない特権ヘルパーを分離し、信頼できる LSM の強制ポイントを創出することが一般的です。

### 6.2 チケット、権限継承、および「代理人問題（Confused Deputy）」

承認されたデーモン、インタプリタ、またはデプロイツールは、攻撃者の制御する入力を受け入れた場合、**代理人問題（Confused Deputy）**を引き起こす可能性があります。短い TTL とオブジェクトにバインドされたチケットはリスクを低減させますが、業務上の意図の正当性までを証明することはできません。TEAL のプロジェクト文書では、主体コンテキスト（Subject-context）およびオブジェクト拘束（Object-bound）の双方のキャッシュ戦略が記述されています。プロセス全体に適用される広範なチケットや継承チケットによって、侵害されたクライアントの代わりに行われる特権操作が無条件に認可されてはなりません。[T1, T2]

推奨される設計原則：アクションと対象スコープの極小化、不要なチケット継承の排除、破壊的操作に対する明示的な例外処理、ポリシーエポック（Policy Epoch）による失効管理、および認可意図と実際の操作を紐付ける監査ログの記録。承認された実行ファイルの署名やハッシュチェック単体では、悪意のある入力を無害化することはできません。

### 6.3 スライディングウィンドウによる大量操作の制御

フリート環境向けに、認証された管理コンテキスト、対象フリート、および時間窓ごとに破壊的操作をカウントするポリシーが提案されています。これは**将来の制御設計**であり、TEAL Alpha で実証済みの機能ではありません。

```text
破壊的操作の実行前：
 実行者および許可された対象を検証；
 （直近のコミット済み操作数 ＋ 今回提案された操作数）をアトミックに検証；
 ポリシーの許容予算内である場合：認可してカウントに加算；
 予算を超過する場合：拒否（DENY）、または厳密にスコープを絞った新たな MPA 承認を要求。
```

カウントと検証の境界は、実行と同期していなければなりません。複数の並行ワーカーが、古いカウンター値を参照して同時にチェックを通過してはなりません。堅牢な設計では、キャンセルされた操作、リトライ、冪等性、部分的な失敗、および複数コントローラーホスト間での集計処理にも対処する必要があります。

### 6.4 計画中の実装ベースライン：信頼できるログイン出自（Login Provenance）

**次期 TEAL リビジョンにおけるコミットされた設計要件（TEAL Alpha では未実装・未検証）。** 本レポートにおける脅威網羅性分析では、以下の 4 つの要件を**「将来のアップグレード後の評価」として明示的にラベル付けされている場合にのみ**仮定できます。実装の実現可能性は文書化された Linux／OpenSSH のプリミティブによって裏付けられていますが、そのセキュリティ保証は正しい統合、カーネルの整合性、およびネガティブパステストに依存します。既存の TEAL v2.2 仕様書（セクション 6.7 および 10.3）では、環境変数とプロセスの親子関係を用いて SSH 接続元を「推測」していましたが、認可目的においてはこの機構を置き換える必要があります。[T1, R17–R22]

1. **環境変数に依存しない出自：** 信頼できる SSH 認証／セッション統合により、実際に受け入れられた TCP ソケットピア（`getpeername` または同等のカーネル派生ピアアドレス）を、認証された UID、成功した認証イベント、およびセッションインスタンスに関連付けます。登録操作は検証された認証ライフサイクルに限定され、`SSH_CLIENT`、`SSH_CONNECTION`、`PAM_RHOST`、ログイン記録、コマンドライン文字列は監査の参考にすることはできても、単独で信頼できる出自を付与してはなりません。最小限の検証済み OpenSSH 側統合、または同等の認証コンポーネントが想定されます。`PAM_RHOST` のみを読み取る汎用 PAM モジュールでは不十分です。なお、記録される送信元 IP は直近に接続されたピアを表すものであり、踏み台、VPN、プロキシ、または NAT の背後にある元のワークステーションを必ずしも表すわけではありません。

2. **カーネル保護された再割り当て不能なアイデンティティ：** 登録されたログインコンテキストは、一意の識別子、ブート識別子、認証済みアイデンティティ、ピアエンドポイント、出自タイプ、確立状態、および出自保証レベルを保持します。これはカーネルが管理する LSM／タスクまたは認証情報に関連付けられた状態として保持され、追記専用（Append-only）または同等に制限された登録ライフサイクルを持ち、非特権ユーザーまたは root による任意の再ラベル付けを禁止し、明示的な破棄／失効ルールを備えます。Linux のイミュータブルな監査 loginuid は関連するメカニズムを示していますが、それ単体では TEAL の送信元 IP や認証イベントを保護しません。登録処理は、単に呼び出し元が UID 0 であることや `sshd` の実行ファイル名であるという理由だけで信頼を付与してはならず、悪意ある root ユーザーがレジストラを呼び出したり注入したりして信頼を偽造することはできなくなっていなければなりません。この保証は、カーネルおよび保護された sshd／TEAL 登録パスが信頼できる状態を維持していることを前提とします。

3. **プロセスおよび認証情報の遷移における保持：** TEAL は、新しい実効 UID を新しい認証済みログイン出自に変換することなく、サポート対象の `fork`/`clone`、`execve`、`sudo`/`su`、および set-UID／認証情報遷移を越えて出自を伝播させます。Linux LSM のタスクおよび認証情報フックが実装ポイントを提供します。プロセスの生成と認証情報の共有ケース、同一 UID 下での並行セッション、切り離された子孫プロセス、PID の再利用、およびセッション終了をテストする必要があります。**独立して起動されたサービスへの委譲**（例：`systemd-run`/D-Bus、既存のデーモン、CI ワーカー、コンテナオーケストレーター）は、*通常の親子間伝播ではありません*。個別に認可され、厳密にスコープを絞った委譲メカニズムが導入されない限り、受信側は独自の出自を維持します。セッション識別子が存在することは、現在のプロセスが未侵害であることを証明するものではありません。

4. **非 SSH 出自の明示的な分類：** サポートされる出自には、`SSH_AUTHENTICATED`、`LOCAL_CONSOLE`、`SERVICE`、`SCHEDULED`、`CONTAINER`（帰属情報が取得可能な場合）、`DELEGATED`、および `UNKNOWN` が含まれます。侵害されたサービス内で実行された Web シェルやリバースシェルのコマンドに、偽装された SSH ログインコンテキストが付与されてはならず、それらはサービス出自を維持するか、不明（UNKNOWN）としてマークされます。高リスクな操作において、出自情報が不完全、未検証、競合、または利用不能である場合は、推測された送信元 IP に基づいて暗黙的に認可することは決して行わず、`DENY`（拒否）とするか、個別に正当化された MPA 決定を要求します。各カテゴリには、コマンド名単体による分類ではなく、明示的かつテストされたエントリポイントのバインディングが必要です。

**ポリシーでの利用：** 意図されている認可タプルは `authenticated_subject + origin_type + trusted_session_id + source_peer + program_identity + operation + protected_object + time/policy_epoch` です。短寿命チケットは、UID や実行ファイル名だけでなく、関連する出自およびポリシーエポックにバインドされる必要があります。チケット継承や Fast Path が出自制限を消去してはなりません。高リスクな管理操作において、これは `EXEC`／ファイル制御および MPA に対する独立した前提条件を追加しますが、それらを置き換えるものではありません。

### 6.5 残余信頼限界と検証義務

この実装は、**侵害されていないカーネルと保護された登録境界のもとで**実現可能であり、任意のカーネル実行に対する保証ではありません。また、強制設計においては、ユーザー空間の root が `sshd`、ポリシーファイル、TEAL デバイス制御、プロセス ché メモリ、読み込まれたプログラム、および信頼できる登録パスを改ざんするのを防ぎ、その前提条件を維持する必要があります。侵害された*正規の*管理者ワークステーション、踏み台ホスト、SSH セッション、またはすでに認可されたプロセスは、依然として正当に見える出自を生成し得ます。そのため、MPA およびアクション／対象のスコープ制限は依然として必須です。SSH プロキシを経由する接続では、エンドツーエンドで別の認証済み出自表明が紐付けられていない限り、直近のピアのみが識別されます。

**次期リビジョンに向けた受入テスト：** 偽造された環境変数／PAM フィールド、同一 UID に対する重複セッション、対話型および非対話型 SSH、SSH マルチプレクシングおよび踏み台ホップ、`sudo`/`su`/set-UID、`fork`/`exec` およびバックグラウンドジョブ、切り離されたデーモンプロセス、`systemd-run` または D-Bus サービスのアクティベーション、cron/systemd タイマー、サービス出自の RCE、root による他セッションコンテキストの登録・置換・盗用試行、セッション失効と PID 再利用、ポリシーエポックおよびチケットキャッシュの変更。未解決のケースについては、高リスクアクションは Fail-Closed（拒否側に倒す）とする必要があります。検証結果は、**技術的実現可能性**、**実装された挙動**、および**指定された攻撃者能力に対する測定された耐性**を明確に区別して報告しなければなりません。[R17–R22]

## 7. 提案された検証実験

### 実験 1 — 稀に実行される破壊的ツール（Beget/Stryker モデル）

**環境:** 隔離された Linux VM およびダミーの顧客データディレクトリ（実際の顧客データは不使用）。  
**セットアップ:** スタンドアロンの `fleet-wipe` または `vm-destroy` 実行バイナリと、独立した通常の監視デーモン。  
**バリアント（検証パターン）:** 非特権ユーザー、盗まれた管理者 UID、承認された操作、拒否された操作、代替ヘルパー、改ざんされたスクリプト、および期限切れ／リプレイされたチケット。  
**合格基準:** 意図された実行ファイルおよび許可された対象セットにバインドされた有効な認可がない限り、破壊的アクションを開始できないこと。管理者権限の侵害を想定した条件下でも同一の保護が維持されること。ブロックされた実際のシステムコール／フック、拒否された操作数、および代替経路によるバイパスの有無を報告する。

### 実験 2 — スケジュールされた管理処理

**環境:** Linux スケジューラが、定義された時間窓内でメンテナンスヘルパーを起動。  
**バリアント:** 時間窓内の実行、時間窓外の実行、対話型シェルからの実行、偽造された環境変数による実行、およびスケジューラ侵害または書き込み可能なジョブ定義による実行。  
**合格基準:** 認証された想定通りのジョブ出自のみが、意図された時間枠内で許可された処理を実行できること。時間窓内であっても、スコープ外の破壊的操作には追加の認可が必要であること。

### 実験 3 — 長時間稼働する管理デーモン

**環境:** ステータス取得と模擬ワイプエンドポイントを提供する管理 API。以下のモデルを比較する：(a) デーモンが内部でワイプを実行、(b) デーモンがゲートされたヘルパーを起動、(c) デーモンがトランザクション認可サービスを呼び出す。  
**合格基準:** 構文的に正当な未認可ワイプリクエストを送信できる攻撃者を、どのモデルが確実に阻止できるかを正確に記録する。この実験により、`EXEC` 単体の制御が不十分となる条件を立証する。

### 実験 4 — 侵害された信頼済みランタイム（Trivy/LiteLLM モデル）

**環境:** 研究者が作成した無害なダミーペイロードを使用する、隔離された CI ランナーおよび Python テスト環境。  
**バリアント:** 承認されたインタプリタによるシークレットファイルの読み出し、子プロセスによるチケットの継承、および未承認宛先への外部送信リクエスト。  
**合格基準:** 拒否されたリソース操作を測定し、プロセスメモリ上にすでに存在するシークレットや、事前に認可された接続を介したリクエストにおける不可避なギャップを文書化する。

### 実験 5 — 不正な業務トランザクション（Arkéa モデル）

**環境:** 模擬台帳および銀行送金 API（実際の資金は不使用）。  
**バリアント:** 盗まれたプロバイダートークン、承認された定常送金、新規に追加された受取人、分割送金、リプレイ攻撃、承認後の内容改ざん、および侵害されたプロバイダーホスト。  
**合格基準:** 銀行側のトランザクション強制機能が、独立した承認のない高リスクまたは改ざんされた指示を拒否すること。これには OS 側の TEAL 制御に加えて、業務レイヤーでの強制が必要であることを明示的に記録する。

### 実験 6 — 信頼できる SSH ログイン出自と出自制約（計画リビジョン）

**環境:** 信頼できる SSH 認証から TEAL への登録パスと、カーネル保護されたセッションコンテキストを備えた隔離 Linux ホスト。  
**バリアント:** 許可されたピアおよび不許可のピアからの認証済み管理者、偽造された `SSH_CONNECTION`、同一 UID による 2 つのセッション、Web サービスによって取得された root、`sudo`/`su`、`systemd-run` 委譲、踏み台ホストおよびマルチプレックス SSH、root による出自の再割り当て試行または無関係なチケットの継承。  
**合格基準:** 高リスクな管理操作が、カーネルレベルで検証可能な一致する出自（および必要に応じた MPA）を持つ場合にのみ許可されること。禁止された送信元とアイデンティティの組み合わせは Fail-Closed すること。プロセス、認証情報、またはサービスの境界を越えてセッション出自の「洗浄（Laundering）」が発生しないこと。検証成功時には、使用された正確なフックとポリシーチェックを特定すること。既存の Alpha の結果を、この基準を満たしていると解釈してはならない。

## 8. カーネル信頼境界を越えた多層防御

### 8.1 スコープと根本的なセキュリティ前提

TEAL の中心的なセキュリティ目標は、**UID 0（root）を取得した攻撃者を含む、ユーザー空間の攻撃者に対する侵害後の強制力**です。しかし、その Linux Security Module（LSM）チェック、ポリシー判定、カーネル内チケット状態、および監査イベントは、同一の Linux カーネル内で実行されるか、カーネルに依存しています。したがって、**カーネルの整合性は明示的な信頼の前提（Trust Assumption）**であり、LSM が単体で証明できるものではありません。Alpha プロトタイプは、任意のカーネルコード実行に対する耐性を主張するものではありません。[T1–T3]

十分なカーネル特権を持って任意のコードを実行できる攻撃者は、LSM フックを変更またはバイパスし、仲介されないカーネルパスを通じて保護されたデータにアクセスし、カーネル生成コンテキストを改ざんし、チケットやプロセス認証情報を操作し、監査ログの収集を無効化し、`teald` またはその通信チャネルを妨害することができます。正しく実装された TEAL ポリシーであっても、その境界が突破された後の強制力を保証することはできません。逆に、任意のカーネル実行を**伴わない** root アカウントの奪取は、それ自体が直ちにカーネル侵害を意味するわけではありません。この区別を維持することが、TEAL の価値提案の根幹です。

本章では、提案する多層防御アーキテクチャにおいて、攻撃者の能力を以下の 4 つの条件に分類します：

| 攻撃者の能力 | TEAL の役割 | 要求される独立した保護策 |
|---|---|---|
| 侵害された非特権プロセス | ポリシー外の `EXEC`、保護されたファイル操作、および仲介されたアクションを拒否 | 通常のパッチ適用、サンドボックス、最小権限の原則 |
| ユーザー空間の root または特権管理サービス（カーネルは健全） | 重大操作ポリシーおよび MPA を強制（検証されたフックカバレッジと堅牢化を前提とする） | 署名済みブートチェーン、保護された TEAL ポリシーおよび登録インターフェース |
| 任意のカーネルレベル実行または同等の制御バイパス | **信頼できる LSM 強制力は保証されない** | ハードウェアを起点とするブート保証、外部監視／隔離、信頼できる復旧 |
| ファームウェア、ハイパーバイザー、ベースボード管理コントローラー（BMC）、物理的トラストルートの侵害 | TEAL の対象外（通常の TPM／ウォッチドッグ運用の対象外となる可能性あり） | 個別に堅牢化されたプラットフォーム／コントロールプレーン、およびインシデント専用の復旧手順 |

したがって、カーネル境界を越えた防御の目的は、**「リスクの低減、外部から可視化できる証拠の確保、被害の封じ込め、および復旧可能性」**であり、TPM 2.0 やウォッチドッグによって侵害されたカーネルを魔法のように信頼できる状態に変えることではありません。保護／検知／復旧の区別は NIST SP 800-193 に準拠していますが、同規格の*主たるスコープはプラットフォームファームウェア*であり、実行時の Linux カーネル整合性の証明ではないことに留意する必要があります。[R23, R31]

### 8.2 侵害前におけるカーネル境界の堅牢化

第一の防御線は、ユーザー空間の root 攻撃者が任意のカーネルコード実行に到達するのを防ぐことです。TEAL の導入において、以下の対策は前提条件または強く推奨されるホスト堅牢化制御として扱われるべきです（ハードウェア、ディストリビューション、およびカーネルビルドによって利用可否は異なります）：

1. **セキュアブート（Verified Boot）と信頼できるアップデートチェーン：** UEFI Secure Boot（サポートされている場合）、適切に署名されたブートコンポーネントおよびカーネル、管理された署名鍵、およびテストされたロールバック／復旧手順により、ブートチェーンの差し替えを防ぎます。Secure Boot は承認された署名を検証するものであり、*ランタイムのエクスプロイト検知器ではありません*。測定と強制は個別に評価する必要があります。
2. **カーネル Lockdown とモジュール読み込み制限：** カーネルメモリを公開したり不正な変更を許可したりするインターフェースを制限し、カーネルモジュールの署名を強制し、モジュール署名秘密鍵を保護します。実際の保護性能は、Lockdown モード、設定、信頼ストア、および代替の読み込みパスが存在するかどうかに依存します。攻撃者が信頼された署名鍵を掌握している場合、署名されたモジュールであっても脆弱であったり悪意を含んでいたりする可能性があります。[R24, R25]
3. **カーネル攻撃面の縮小：** タイムリーなカーネルアップデートを適用し、制限のないモジュール読み込み、危険なデバイスアクセス、デバッグ機能、不要に露出した特権サブシステムなど、不要な特権インターフェースやカーネル機能を無効化または制限します。これらはリスクを低減させますが、未知のカーネル脆弱性を完全に排除することはできません。
4. **TEAL 自身のコントロールプレーンの保護：** `teal_module`、`/dev/teal` 制御操作、`teald` 実行ファイル、読み込まれたポリシー／バンドル、ロール定義、SSH 出自レジストラ、認可鍵、およびポリシーエポック／チケット遷移は、侵害されたユーザー空間の管理者によって書き換え、置換、または勝手な再設定ができてはなりません。強制力を持つチェックは、それが検証するアイデンティティの主張から独立していなければなりません。
5. **可能な限り MPA 承認権限を侵害ホストの外部に保持：** 独立した承認者と署名鍵の厳重な保管により、単一の root 侵害によって破壊的操作の要求と承認の両方が行われてしまうリスクを低減します。ただし、カーネルが侵害されたホストが単に LSM ゲート自体をバイパスできる場合には効果を持ちません。

これらの制御は、製品名やパッケージのインストール状況から推測するのではなく、*実際のカーネル構成およびブート状態*に基づいて検証されなければなりません。例えば、寛容な（permissive）モジュール署名チェックと、強制的な署名検証は実質的に全く異なります。[R24]

### 8.3 TPM 2.0、メジャードブート、およびリモートアテストステーション

TPM 2.0 は、プラットフォーム構成レジスタ（PCR: Platform Configuration Register）に測定値を記録し、アテストステーションキー（AK）を用いて暗号学的な **Quote（引用証明）**を生成できます。メジャードブート設計では、信頼されたファームウェアとそれに続くブートコンポーネントが、測定値を PCR に順次拡張（Extend）していきます。独立した検証者（Verifier）は、新鮮なノンス（Nonce）を用いてプラットフォームにチャレンジを送り、Quote の署名とプラットフォームアイデンティティを検証し、PCR の証跡を承認されたポリシーと比較し、関連するイベントログを署名された PCR 状態と照合します。これにより、想定された測定チェーンのもとで**「測定されたイベントとその整合性」に関する証拠**が確立されます。ただし、これはその後のすべてのメモリ操作が無害であったことを証明するものではありません。[R27]

提案される TEAL アテストステーションフローを以下に示します。Keylime などのオープンソースプロジェクトは、独立したレジストラ／検証者が TPM Quote や IMA 証跡をどのように処理できるかを例示していますが、本レポートは Keylime がすでに TEAL に統合されていることを前提とするものではありません。[R30]

```text
ハードウェア / ファームウェアによる測定の信頼の基点（Root of Measurement）
 |
 v
UEFI / ブートコンポーネント / カーネルおよび承認されたブートポリシー
 |
 v
TPM PCR 測定値 + 測定/イベントログ
 |
 [TEAL ホスト・アテストステーションエージェント]
 | 署名済み Quote(nonce, 選択された PCR) + イベント証拠
 v
 独立したリモート検証者（Verifier）
 |
 承認（Approved） / 不信頼（Untrusted） / 利用不可（Unavailable）
 |
 v
外部のアドミッション（接続許可）または隔離コントローラー
```

**実効性のあるアテストステーションのための設計要件：**

- TPM アテストステーションアイデンティティのプロビジョニングと認証。検証者が生成したノンスによる鮮度（Freshness）の検証、およびリプレイ攻撃や検証不能なイベントログの拒否。
- どのファームウェア、ブートローダー、カーネル、initramfs、ブートパラメータ、および TEAL 関連成果物が測定の対象となるかを厳密に定義すること。**該当する成果物を実際に含んでいない PCR から、TEAL の存在やポリシーの整合性を推測してはならない。**
- 承認された測定ベースライン、署名されたメンテナンス変更、カーネル／ファームウェアの更新遷移、およびロールバックポリシーの管理。正常なアップグレードによっても PCR は変化し、それは攻撃ではありません。
- 検証者の鍵、判定ロジック、およびログを、測定対象ホストの外部に保持すること。証拠の欠落、無効な Quote、タイムアウトは**「未証明（Not attested）」**として扱い、直ちに確定的な侵害として決めつけるべきではありません。
- 可能な限り、ネットワーク接続の許可や重要なリモートサービスへのアクセス権を、起動時の一回限りのチェックではなく、直近のアテストステーション成功と短い認可リース期間に連動させること。

**重要な制限事項：** マシンが正規のカーネルを起動し、承認された Quote を生成した後に、ブート PCR が承認ベースラインと一致したままランタイムのカーネルエクスプロイトを受ける可能性があります。また、変更されていないブート PCR を定期的に再 Quote するだけでは、カーネルメモリを改ざんした攻撃者を検出することはできません。TPM は自身の署名操作と測定レジスタを保護するのであり、カーネル RAM の汎用的なライブスキャナーではありません。[R27]

さらに、TPM の**シーリング（Sealing）**機能を用いて特定の秘密情報を特定の PCR 値にバインドすることで、プラットフォームが未認可の測定状態で起動された場合にその秘密情報へのアクセスを阻止することができます。しかし、OS が秘密情報のアンシールに成功し、平文や鍵データをメモリ上に保持した後は、その後のカーネル侵害によって露呈する可能性があります。より価値の高い鍵については、サポートされ適切に統合されている場合、侵害されたホストに平文鍵を露出させない外部 HSM や専用ハードウェア内で機密暗号操作を実行し続けるべきです。[R29]

### 8.4 ランタイムファイル整合性制御：IMA/EVM とその限界

Linux の Integrity Measurement Architecture（IMA）は、*測定（Measurement）*、*評価（Appraisal）*、および*監査（Audit）*ポリシーをサポートしています。測定機能はイベントログを生成し、完全性ハッシュを TPM の PCR に拡張できますが、**測定単体では実行を阻止しません**。評価機能は、ポリシーが実際に強制されている限り、設定されたハッシュまたは署名ポリシーに適合しないファイルへのアクセスを拒否できます。EVM は、完全性の判定に使用されるセキュリティ関連の拡張メタデータを保護できます。[R26]

堅牢化された TEAL 環境において、慎重にスコープを絞った IMA 評価ポリシーを適用することで、信頼できる SSH 出自、`teald`、および重要な管理ヘルパーを支える実行バイナリやポリシー成果物を保護できます。また、IMA 測定機能は、独立した検証者が実行時に読み込まれた選択ファイルや設定の変更を評価するのに役立ちます。そのためには、ファイルセット、読み込み順序、評価モード、ポリシー署名の強制、および更新手順を明確に定義してテストする必要があります。関連するすべてのファイルが自動的に網羅されると見なしてはなりません。

IMA および TPM の証拠は、狭義に解釈されるべきです：

- これらは**測定または評価されたファイルの変更**を防止または察知する能力を向上させますが、認可されたプロセスの*ランタイムメモリ*が完全であることを自動的に証明するものではありません。
- カーネルを攻撃する者は、測定対象の実行ファイルを改変することなく、実行フローを変更できる可能性があります。カーネルの整合性が失われると、悪意のあるカーネルは将来の測定を抑制したり、他のローカルインターフェースを介して偽証したりする可能性があります。TPM 署名された履歴は、将来のイベントが省略されていないことを証明するものではありません。
- リモート検証では、イベントログと関連 PCR との整合性を検証する必要がありますが、検証の成功は**示された前提条件のもとでの測定履歴**を確立するものであり、包括的なランタイム整合性を保証するものではないことを認識しておく必要があります。
- IMA は TEAL のアクション認識ポリシーを代替することはできません。完全に署名された正規の管理ツールであっても、未認可の操作を実行するために悪用される可能性があります。

独立したランタイムメモリ監視（例：適切に隔離されたハイパーバイザーまたはハードウェア支援によるインスペクション）は別個の研究として考慮できますが、**現行の TEAL Alpha の保証範囲には含まれません**。そのような監視機構もまた、カバレッジ、パフォーマンス、および信頼境界の制限を抱えています。[R26, R27]

### 8.5 ウォッチドッグ、外部監視、および封じ込め

従来の Linux **ハードウェア・ウォッチドッグ・タイマー**は、主として死活監視の失敗（Liveness failure）を検知します。ローカルプロセスまたはウォッチドッグドライバからのキープアライブ信号（Keepalive）の供給が途絶えた場合、ハードウェアは設定されたタイムアウト後にマシンをリセットできます。これにより、必須コンポーネントをクラッシュまたは無効化させる一部の攻撃を含め、システムのハングアップからの可用性と復旧性を高めることができます。しかし、これは**任意のカーネル侵害を検知するものではありません**。高度なカーネル攻撃者は、キープアライブの送信を継続したり、ハードウェア／ドライバの設定が許せば機構自体を無効化したりすることが可能です。ドライバの動作および `nowayout` のサポート状況はプラットフォームによって異なります。[R28]

カーネルへの脅威に対して実効性を持たせるには、監視および**対応権限（Response authority）**を、可能な限り*疑わしいカーネルの外部*に配置する必要があります。外部の検証者または管理コントローラーは、アテストステーション証跡の欠落、アプリケーションレベルのチェック失敗、サービスの喪失、予期しない管理プレーンのアクティビティ、または独立したチャネル経由で受信したアラートなど、独立したシグナルを監視できます。それでもなお、もっともらしく振る舞い続ける悪意あるカーネルは、これらのチェックを回避する可能性があります。ウォッチドッグのハートビートはある種の生存を示す証拠ではあっても、**信頼性（Trustworthiness）を示す証拠ではありません**。

実用的な役割分担は以下の通りです：

| メカニズム | 確立または引き起こすことができる事象 | 保証できないこと |
|---|---|---|
| ホスト内ウォッチドッグデーモン ＋ ハードウェアタイマー | ローカルキープアライブ途絶後のシステムリセット | 潜伏中または協調的なカーネル攻撃者の検知 |
| リモートハートビート／サービスプローブ | 特定の疎通性またはサービス障害の検知 | カーネルメモリ整合性の証明 |
| TPM Quote ＋ 承認されたイベント証拠 | 指定された測定値とその鮮度の認証 | 測定対象外のランタイムコード実行の検知 |
| 外部ネットワークスイッチ／独立ゲートウェイ | ローカルファイアウォール規則が無効化されてもホストの通信を遮断 | すでに進行中のローカルディスク破壊の全停止 |
| 独立管理された復旧コントローラー | リセット、レスキューメディアでのブート、本番再投入のゲート | 盗難されたデータの回収、永続ファームウェア侵害の自動排除 |

**レスポンスプレーンの完全分離が不可欠です。** 疑惑のあるホスト自身が、自らの隔離ルールを解除したり、リモート検証者の判定を書き換えたり、管理コントローラーの認証情報を変更したり、本番への復帰を自己承認できたりしてはなりません。管理コントローラーやスイッチ自身も堅牢化され、アクセス制御、監視、アップデートが行われる必要があります。侵害されたホストからのコマンドを独立した認証なしに受け入れる BMC は、十分な隔離境界とは言えません。

運用上は、**健全（Healthy）**（証拠がポリシーを満たす）、**不信頼（Untrusted）**（証拠がポリシーと矛盾する）、**不明／利用不可（Unknown/Unavailable）**（証拠を取得できない）の 3 つの状態を明確に区別します。「不明」は侵入の証明ではありませんが、証拠が得られないという理由だけで高リスクな特権を付与してはなりません。可用性と封じ込めのバランスをとるため、適切な隔離またはデグラデーション（性能縮退）ポリシーを事前に策定しておく必要があります。

### 8.6 提案される多層防御アーキテクチャとインシデントレスポンス

以下の*将来的*アーキテクチャは、ローカルでの強制力、証拠の検証、およびそれに伴うレスポンス処理を分離します。これは提案であり、現在の Alpha 実装の仕様ではありません：

```text
 信頼ドメイン A（TRUST DOMAIN A）: 保護された Linux ホスト
 +-----------------------------------------------------+
 | 署名/メジャードブート -> Linux カーネル -> TEAL LSM |
 |       |                    |              |         |
 |    TPM 2.0             IMA 評価        teald / MPA  |
 |       |                    |              |         |
 |   TPM Quote    +      IMA 証拠     + ハートビート/監査|
 +--------------------------|--------------------------+
                            | 認証済みテレメトリ
                            v
 信頼ドメイン B（TRUST DOMAIN B）: 独立した検証者 / ログストア
 +-----------------------------------------------------+
 | ノンス/Quote検証、承認済み測定値との照合、          |
 | タイムアウト監視、アラート相関分析、追記専用証跡保持|
 +--------------------------|--------------------------+
                            | 署名/認可された決定通知
                            v
 信頼ドメイン C（TRUST DOMAIN C）: 独立したレスポンスプレーン
 +-----------------------------------------------------+
 | ゲートウェイ/スイッチによる隔離、サービスアクセス取消|
 | BMC または独立ウォッチドッグによるリセット、        |
 | レスキューブート、クリーン再イメージング、再投入前アテスト|
 +-----------------------------------------------------+
```

検証プレーンとレスポンスプレーンは、**耐侵害性と管理上の分離が維持されている場合に限り**、小規模な環境において統合することができます。単一の管理者認証情報が TEAL ホスト、検証者、スイッチ、バックアップ、および復旧イメージのすべてを掌握してしまう「共通要因破壊（Common-mode failure）」を防ぐ必要があります。特権を分離し、例外的な操作には独立した承認を用います。これは、未検証の詳細を特定の事案に帰することなく、ケーススタディで浮き彫りになった*管理権限の集中リスク*に直接対処するものです。

信頼できるアラートや整合性検証の失敗を受けた、安全側の対応シーケンスは以下の通りです：

1. **分類と確認：** アラート時刻、ホストアイデンティティ、最終承認されたアテストステーションとポリシーエポック、直近の承認／チケットアクティビティ、およびどのセンサーや条件が失敗したかを記録します。単一の ping 応答途絶から直ちにカーネル侵害を断定してはなりません。
2. **外部からの隔離：** 機密サービスへのアクセスを取り消し、**疑惑のホストによって管理されていない**ネットワークゲートウェイまたはスイッチにおいて隔離を適用します。必要に応じて、個別に認証されたフォレンジック用または復旧用のパスを確保します。
3. **証拠の適切な保全：** リモートの監査／アテストステーション記録を保持し、インシデントポリシーが許せば、管理されたツールを用いてフォレンジックイメージまたはメモリ証拠を取得します。侵害された可能性のあるカーネルのローカルログの内容は、単体で信頼できるものではありません。稼働状態での証拠取得（ライブアクイジション）は証拠を汚染したり、調査者を悪意あるコードに晒すリスクがあります。
4. **権限の取り消しとローテーション：** 影響を受けたセッション、チケット、サービス認証情報を無効化し、署名鍵および SSH／管理アクセスを見直し、バックアップ削除やデプロイ権限を制限します。危険に晒されるのは root 認証情報だけではありません。
5. **独立した信頼源からの復旧：** 検証済みのイメージから再インストールまたは再イメージングを行います。関連するファームウェアおよび管理コントローラーの整合性を検証し、TEAL とそのポリシーを再インストールし、独立して保護され整合性チェックに合格したバックアップからデータを復元します。**不信頼となった環境の単なる再起動は、復旧と同義ではありません。**
6. **本番再投入前の再アテストステーション：** 新鮮なメジャードブート証跡と承認されたポリシー状態を要求し、外部隔離を解除する前に機能およびセキュリティチェックを実行します。復旧の監査証跡を維持し、初期侵入経路への対策が完了していることを確認します。

ハードウェアウォッチドッグは一部の障害状態においてリセットを開始できますが、自動的にリセットするか、あるいは証拠保全のために一時停止するかは、運用上明示的に選択すべき事項です。無条件の自動リブートは揮発性のフォレンジック証拠を消去したり、侵害された同一環境への再起動を繰り返すリスクがあります。重要なデータを保持するホストにおいては、無条件のリブートよりも、**まず外部隔離**を行い、その後に管理された復旧を進める方が安全です。

### 8.7 TEAL 固有の障害モードと検証可能な保証

システム統合においては、任意のカーネル侵害とは切り離して `teald` 自身の障害を考慮しなければなりません。TEAL v2.2 の設計では、デーモンが利用不能になった場合、デーモンの判定を必要とする新たな Slow Path 操作を拒否する一方、依然として有効な Fast Path チケットはより厳格な構成によって明示的に取り消されない限り使用を継続できるという **Fail-Safe** 動作を規定しています。そのウォッチドッグおよびネットワークロックダウンに関する側面は*仕様または提案*であり、Alpha の実証済み防御策として確立されたものではありません。[T1]

この区別は運用上の帰結をもたらします：

- `teald` のハートビート途絶は、**カーネルの強制力が依然として信頼できる間は**ローカルの Fail-Safe ルールをトリガーすべきであり、外部アラームを個別にトリガーしても構いません。しかし、これはカーネルが健全であることを証明するものではありません。
- 既存のチケット、特にプロセスにバインドされた広範なチケットや継承されたチケットは、デーモンの停止中にも操作を許可してしまう可能性があります。高保証プロファイルでは、それらを失効させるべきか、処理中の操作をどう扱うか、そして古いチケットがポリシー遷移を越えて生き残るのをどう防ぐかを定義する必要があります。
- `/dev/teal` の保護、ポリシー更新、デーモン登録、監査状態、および提案されている SSH 出自登録チャネルは、**カーネル侵害前**の堅牢化課題の一部です。外部アテストステーションは、これらの制御を強制することの代替として記述されるべきではありません。
- 外部の検証者は、カーネル侵害後にローカルの TEAL 監査記録が完全であると仮定することはできません。追記専用のリモートシンクに監査イベントを送信することは証拠保全性を高めますが、すべてのイベントが確実に生成されたことまでは保証しません。
- 復旧後のサービスアクセスは、ホストが合意された復旧およびアテストステーションチェックに合格した後にのみ、外部のアドミッションコントローラーによって付与されるべきです。攻撃者の制御可能なローカルの `ENFORCE` ステータス文字列を信用してはなりません。

**本レポートで採用すべき防御の主張：**  
*TEAL は、カーネルおよびポリシー強制パスが信頼できる状態を維持している間、ユーザー空間の特権侵害に対して重要操作ポリシーを強制できます。検証済み／メジャードブート、IMA、TPM による証拠、独立した監視、外部隔離、および信頼できる復旧は、その境界を越えたリスクを低減しレジリエンスを向上させることができますが、任意のランタイムカーネル侵害の検知や防止を完全に保証することはできません。*

### 8.8 実験的検証と提案されるロードマップ

多層防御レイヤーは、既存のファイル／実行ベンチマークとは切り離してテストする必要があります。以下は**提案されるテストケース**であり、完了した TEAL の検証結果ではありません：

| テストケース | 制御された障害／攻撃シミュレーション | 証拠および合格基準 |
|---|---|---|
| B1 — 未承認ブート成果物 | 未承認のテストカーネルまたは改変された署名ブート構成で起動 | 設定に応じて、Secure Boot による拒否またはリモートアドミッションによる拒否が発生すること。どのコンポーネントが決定を執行したかを明記する。 |
| B2 — 測定対象ファイルの改ざん | 隔離されたイメージ内で保護されたテスト実行ファイルまたは TEAL 関連設定を改ざん | 強制モードの場合、IMA *appraisal* が対象アクセスをブロックすること。または設定に応じて測定により検証者から可視の差異が生成されること。カバレッジのギャップを報告する。 |
| B3 — Quote リプレイ／異種プラットフォーム | 過去の Quote をリプレイするか、不一致の認証アイデンティティを使用 | 検証者が、古いノンス、誤った鍵、または不整合な PCR／イベントログの証跡を拒否すること。 |
| B4 — `teald` 障害 | ポリシーデーモンのみを停止/kill（テストカーネルの信頼性は維持） | 正確な Slow Path の拒否、Fast Path チケットの保持／失効状況、外部通知を記録し、復旧遷移を検証する。 |
| B5 — ステルスカーネル侵害モデル | 認可されたラボ環境下で、**ローカル**の強制力をバイパスしながらハートビートを送信し続ける侵害ホストをエミュレート | ハートビートのみの検知では不十分であることを実証し、真に独立した測定やプローブによって生成された検知のみを報告する。包括的なカーネル侵害検知を主張してはならない。 |
| B6 — 外部隔離 | 完全性検証の失敗または許容証拠の途絶をシミュレート | ローカルファイアウォールが許可し続けている場合でも、独立したスイッチ／ゲートウェイが指定された外部および管理アクセスをブロックすること。 |
| B7 — 信頼できる復旧 | 不信頼となったテストイメージを再起動し、その後既知の正常イメージに置き換え | 再起動単体では認可が再確立されないこと。本番再投入の前に、検証済み再イメージングと新鮮なアテストステーションが必要であること。 |
| B8 — コントロールプレーン侵害 | テスト管理者に保護対象ホストの root 権限を付与（ただし検証者／スイッチや承認鍵の権限は付与しない） | ホスト側から外部ポリシーの変更、リモート証跡の消去、隔離の解除、自らの本番復帰の承認ができないこと。 |

**実装の順序（シーケンス）：**  
(i) root 侵害とカーネル侵害の脅威境界を文書化して検証する；  
(ii) セキュアブート、カーネルモジュール読み込み、および TEAL のローカルコントロールプレーンを堅牢化する；  
(iii) 測定スコープを明確にした TPM ベースのリモートアテストステーションの概念実証（PoC）を構築する；  
(iv) 独立して管理される隔離機構と慎重に設定されたウォッチドッグ動作を統合する；  
(v) クリーンな復旧、鍵のローテーション、および再投入手順を演習する；  
(vi) 残された脅威モデルによって複雑さが正当化される場合に限り、より強力なランタイム完全性計測の導入を検討する。

提案されている保護策は相互に補完し合うものであり、代替可能なものではありません。特に、**ブート時のアテストステーション成功を、稼働中のアクティブなカーネルが未侵害であることの証明として報告してはなりません**。最終的な研究成果においては、*強制された操作、測定されたカバレッジ、検証の鮮度、独立した対応能力、および残余の信頼前提*を、それぞれ独立した結果として報告する必要があります。[R23–R31, T1–T3]

## 9. 結論

1. **Beget および Stryker は、管理操作リスクの強力な実例を示している。** 破壊的機能を、独立して呼び出し頻度の低い専用ヘルパープロセス経由でのみ実行できるように再設計した Linux 環境は、TEAL の `EXEC` 制御および MPA に極めて適しています。ただし、実際のインシデントにおいてそのようなヘルパーが存在していたことは確認されていません。
2. **呼び出しモデルが決定的である。** 稀に実行されるユーティリティやスケジュール実行されるユーティリティは、比較的シンプルな実行ポリシーで管理できます。自ら危険な処理を実行する常駐型コントローラーに対しては、実際の操作により近いポイントでのチェックが必要です。
3. **Crédit Mutuel Arkéa は 2 つの信頼境界を跨いでいる。** 侵害されたサードパーティの Linux 環境において TEAL が寄与した可能性は考えられますが、最終的な資金保護のためには、正確かつリプレイ不能なトランザクションに対する銀行側の承認ポリシーが不可欠です。委託先側の根本的な侵入原因は公には解明されていません。
4. **Ivanti は、侵害後の極めて具体的な `EXEC`／ファイル制御シナリオを示している。** Trivy と LiteLLM はその逆を示しています。すなわち、マルウェアが信頼されたデプロイツールやインタプリタの内部で実行される場合があり、プログラムの名前よりも正確なリソース権限およびネットワーク権限の制御が重要となります。
5. **信頼できるログイン出自は次期リビジョンのコミットされた設計であり、Alpha の成果ではない。** カーネルから派生する SSH ピア情報、認証済みセッション登録、カーネル保護されたアイデンティティ、継承ルール、および非 SSH 出自の分類は、明示的な実装要件です。そのセキュリティ価値は検証された登録処理と Fail-Closed ポリシーに依存します。信頼できる出自であっても、セッションが未侵害であることを証明するものではありません。
6. **過大主張を避けること。** これらは制御マッピングの仮説およびラボでのテスト計画であり、TEAL が実インシデントの被害を確実に阻止できたという遡及的な証明ではありません。TEAL Alpha は現時点で、カーネル侵害、すべての管理 API、または業務レベルのトランザクションに対する完全な保護を確立するものではありません。
7. **カーネル侵害は独立した信頼ドメインである。** TEAL が LSM の判定を強制するには健全なカーネルが必要です。提案された TPM、完全性制御、外部監視、隔離、および復旧メカニズムはレジリエンスと証拠の質を向上させますが、水面下で進行するランタイムカーネル奪取の検知を完全に保証することはできません（第 8 章）。

**全体を貫く命題（Overall Thesis）：**  
被害が発生する直前の、信頼して強制執行できる最後のポイントにおいて、最も複雑度の低い信頼可能なゲートを適用すること。めったに使われない破壊的プログラムに対しては、それは `EXEC` ＋ MPA であり、常駐型コントローラーに対しては破壊的管理操作そのもののゲートであり、銀行システムに対しては個別の送金トランザクションの承認です。
